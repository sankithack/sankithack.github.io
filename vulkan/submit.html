5 · Submission & synchronization

Submission turns recorded command chunks into one CS ioctl. The ioctl carries IB descriptors, a BO list and syncobj wait/signal lists. The kernel validates it, queues a job, and eventually writes an INDIRECT_BUFFER packet into a hardware ring. Fences and semaphores are DRM syncobjs throughout.

The path in one paragraph

vkQueueSubmit → Queue::Submit (XGL) queues the semaphore waits, collects each command buffer's Pal::ICmdBuffer, and calls IQueue::Submit. PAL's core Queue::SubmitInternal associates fences and calls OsSubmit. The amdgpu backend builds the BO list from residency references, turns each command stream into an IB, packs IB + syncobj + BO-list chunks, and calls libdrm amdgpu_cs_submit_raw2, which issues DRM_IOCTL_AMDGPU_CS. In the kernel, amdgpu_cs_ioctl parses and validates and pushes a job to the DRM GPU scheduler. When its dependencies resolve, amdgpu_job_run → amdgpu_ib_schedule writes the IB pointers and a fence into the ring.

Step-through: vkQueueSubmit → ring, then fences & semaphores

IBs and rings

An IB is just {va_start, ib_bytes, ip_type, ring, flags} (drm_amdgpu_cs_chunk_ib): a pointer to PM4 that PAL already wrote into GPU memory. PAL submits one IB per command stream: the stream's first chunk, with the remaining chunks reached by chaining. The IP type selects the ring family:

Each PAL queue owns a kernel context (amdgpu_cs_ctx_create2, via CreateCommandSubmissionContextRaw). The CS ioctl names that context, and the kernel returns a per-context sequence number that identifies the submission.

BO lists

Every BO the GPU may access must be in the submission's BO list, unless it was created VM_ALWAYS_VALID. PAL builds the list in UpdateResourceList from the device-global references XGL registered at allocation time (Topic 2) and reuses the previous list when nothing changed. On current kernels the list goes inline in the CS ioctl as an AMDGPU_CHUNK_ID_BO_HANDLES chunk. On the legacy path PAL first creates a kernel list object (DRM_AMDGPU_BO_LIST, via amdgpu_bo_list_create_raw) and passes its handle instead. In the kernel, amdgpu_cs_parser_bos locks and validates every listed BO before the job may run.

The design rests on one trick: every CS ioctl signals the queue's private syncobj (m_lastSignaledSyncObject, appended to the signal chunk). Anything that must signal when that submission finishes, whether a VkFence or a Vulkan signal semaphore, gets a copy of that fence through ConveySyncObjectState. That function uses amdgpu_cs_syncobj_transfer, or a sync-file export/import as a fallback. Waits are never done on the CPU: they become kernel scheduler dependencies, so a submission blocked on a semaphore costs no CPU time.

Ioctl-level detail for the syncobj chunks is in the kernel's amdgpu_cs_p2_syncobj_in, amdgpu_cs_p2_syncobj_timeline_wait, amdgpu_cs_p2_syncobj_out and amdgpu_cs_p2_syncobj_timeline_signal (amdgpu_cs.c).

The kernel side

amdgpu_cs_ioctl runs a fixed sequence: amdgpu_cs_parser_init → amdgpu_cs_pass1 (copy and parse chunks) → amdgpu_cs_pass2 (IBs, syncobj dependencies) → amdgpu_cs_parser_bos (lock and validate BOs) → amdgpu_cs_patch_jobs → amdgpu_cs_vm_handling (page tables up to date) → amdgpu_cs_sync_rings → amdgpu_cs_submit, which calls drm_sched_entity_push_job. The DRM scheduler later calls amdgpu_job_run, which calls amdgpu_ib_schedule. For each IB, the ring's emit_ib (e.g. gfx_v11_0_ring_emit_ib_gfx) writes an INDIRECT_BUFFER packet with the IB address and the process's VMID. The CP then executes PAL's PM4 using the process's page tables.

The kernel checkout is newer (2026) than the AMDVLK sources (2025-04). Newer uAPI (e.g. AMDGPU_USERQ user-mode queues, visible in the ioctl table) is never issued by PAL's amdgpu backend in these sources.

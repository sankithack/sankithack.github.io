AMDVLK, from vkCmdDraw to the GPU ring

An interactive guide to AMD's open-source Vulkan driver, built from its actual source code. Every class, function and file named here exists in the pinned checkouts, and every code panel links to the exact lines on GitHub or GitLab.

Project status: discontinued, repositories archived

AMDVLK is discontinued. The first line of the AMDVLK README reads “This project is discontinued” (with a link to discussion #416). The GitHub API reports the xgl, pal, llpc and llvm-project (GPUOpen fork) repositories as archived (read-only). The top-level AMDVLK repository is not marked archived, but its README carries the notice. The final xgl/pal/llpc commits are dated 2025-04-29.

libdrm and the Linux amdgpu driver are actively developed. Their checkouts here are newer (2026) than the AMDVLK code, so kernel line numbers match the pinned Linux SHA, not necessarily the kernel AMDVLK was last tested on. See Sources, SHAs & status.

The stack, layer by layer

Click a layer for its responsibilities, its key classes and links into the code. On each topic page, a smaller copy of this diagram follows the stepper and highlights the layer the current step runs in.

LLPC is drawn beside XGL because it isn't a layer that calls go through. It is a compiler library that XGL calls into (Llpc::ICompiler::Create) and that returns an ELF. PAL then loads that ELF.

Start here: a reading order

  1. Architecture & loader entry: how the Vulkan loader finds the driver, how a VkDevice handle becomes a C++ object, and how XGL objects own PAL objects. Read this first; the patterns repeat everywhere.
  2. Memory allocation: the simplest end-to-end path through all six software layers, and the place to learn the BO/VA/residency vocabulary used in every later topic.
  3. Command buffers & PM4: what recording a draw actually writes, with a bit-level breakdown of a real DRAW_INDEX_AUTO packet.
  4. Submission & sync: how those command chunks become IBs in a CS ioctl, how the kernel puts them on a ring, and how fences and semaphores map to DRM syncobjs.
  5. Shader compilation: the deepest topic: SPIR-V → LLVM IR → LGC → AMDGPU ISA → ELF → PAL. Read it last, or first if compilers are your thing.
  6. Keep the glossary open. Dotted-underlined terms show definitions on hover. Press / to search.

Five facts that surprise newcomers

  1. This PAL and LLPC cannot target GFX9 (Vega). PAL's GfxIpLevel starts at GfxIp10_1 and LLPC asserts gfxIp.major >= 10. The AMDVLK README sends pre-GFX10 users to the 2023.Q3.3 release. This site therefore covers GFX10, GFX11 and GFX12.
  2. PAL's hw/gfxip/gfx9 directory is the GFX10–GFX11.5 hardware layer. Device creation sends 10.1, 10.3, 11.0 and 11.5 to Gfx9::CreateDevice. Only GFX12 has its own layer.
  3. Reserving GPU virtual address space never reaches the kernel. libdrm's amdgpu_va_range_alloc is a user-space allocator. The kernel first sees the address when a BO is mapped there with DRM_AMDGPU_GEM_VA.
  4. Every VkDeviceMemory is resident for its whole life. XGL adds each allocation to PAL's device-global reference list at creation (Device::AddMemReference), and that list becomes the BO list of every submission.
  5. Shader modules aren't compiled to ISA. vkCreateShaderModule only hashes and preprocesses the SPIR-V. Codegen happens per pipeline, because LGC needs vertex formats, color formats and the descriptor layout to lower the shaders.

How to read the code panels

  • The header shows repo / path Lstart–end. The link opens the full file at the pinned commit, with those lines highlighted.
  • Excerpts are cut from the source by a script (tools/build.py), never retyped. They are at most 30 lines, so they often stop mid-function; follow the link for the rest.
  • Each panel has an Explain note in plain language. Where something couldn't be traced from the cloned source, the page says not traced rather than guessing.

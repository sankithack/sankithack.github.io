Architecture & loader entry

Three AMD libraries make up the driver, and each has one job. XGL speaks Vulkan. PAL speaks GPU and OS. LLPC turns SPIR-V pipelines into machine code. This page shows how they connect and how a Vulkan call enters them.

The dependency arrows only point one way. XGL calls PAL interfaces (Pal::IDevice, Pal::IGpuMemory, Pal::ICmdBuffer, Pal::IQueue) and the LLPC interface (Llpc::ICompiler). PAL calls libdrm. The two libraries never call each other: the only thing that moves from LLPC to PAL is the ELF blob, and XGL carries it.

Step-through: from loader to PAL

Worked example: what happens when an app calls vkCmdDraw

PFN_vkCmdDraw pfnDraw = (PFN_vkCmdDraw)vkGetDeviceProcAddr(device, "vkCmdDraw");
pfnDraw(cmd, 3, 1, 0, 0);   /* or plain vkCmdDraw(cmd, 3, 1, 0, 0) through the loader */
  1. Lookup: vkGetDeviceProcAddr uses the device dispatch table (vk_dispatch.cpp). GetEntryPoint finds vkCmdDraw in g_EntryPointMetadataTable, sees it is a DEVICE-level entry point, and returns XGL's vk::entry::vkCmdDraw. Calling the returned pointer skips the loader's trampoline; calling vkCmdDraw directly goes through the loader, which reads the dispatch pointer from the first word of the VkCommandBuffer.
  2. Handle to object: VkCommandBuffer is dispatchable, so it points at a Dispatchable<CmdBuffer>. ApiCmdBuffer::ObjectFromHandle skips the VK_LOADER_DATA word to reach the CmdBuffer object (pointer arithmetic).
  3. XGL to PAL: CmdBuffer::Draw calls ICmdBuffer::CmdDraw on the PAL command buffer it owns, once per GPU in the device mask.
  4. PAL to hardware layer: the call jumps through m_funcTable into the GFX10/11 or GFX12 hardware layer chosen at device creation. Topic 4 follows it down to PM4.

Every arrow in this chain is a direct call or a table jump in user space. Nothing reaches the kernel until vkQueueSubmit.

Loader entry and dispatch tables

The Khronos loader reads amd-icd.json, loads the library, and calls vk_icdNegotiateLoaderICDInterfaceVersion. XGL accepts interface versions 3 through 6. From then on, every function pointer the loader hands the application comes from vk_icdGetInstanceProcAddr.

XGL keeps three kinds of DispatchTable. The global table, g_GlobalDispatchTable, answers before an instance exists. Each instance has a table filtered by the enabled API version and instance extensions, and each device has one filtered by device extensions. Every table is filled by the same DispatchTable::Init, which pairs each name with the internal vk::entry:: implementation.

Handles are pointers; the loader owns the first word

For dispatchable handles (VkInstance, VkPhysicalDevice, VkDevice, VkQueue, VkCommandBuffer), the loader writes its own dispatch pointer into the first pointer-sized word of the object. XGL's Dispatchable<C> template reserves that word as VK_LOADER_DATA (seeded with ICD_LOADER_MAGIC) and stores the real C++ object right after it. ObjectFromHandle converts a handle into a pointer to that object.

Non-dispatchable handles (VkDeviceMemory, VkBuffer, VkPipeline…) need no loader word. NonDispatchable<> just casts the 64-bit handle to a pointer.

XGL objects wrap PAL objects

Almost every XGL object holds one PAL object per GPU in the device group, and PAL never allocates CPU memory for API objects itself. XGL first asks PAL how big its object is (e.g. GetGpuMemorySize, GetFenceSize, GetCmdAllocatorSize), then usually makes one allocation (semaphores are an exception and allocate the two separately) through the application's VkAllocationCallbacks holding [XGL object][PAL object × N GPUs], and finally calls PAL's Create* with a placement address inside it.

Where LLPC is invoked

Each PhysicalDevice has a PipelineCompiler. During initialization it converts PAL's GfxIpLevel into a Vkgc::GfxIpVersion and creates the Llpc::ICompiler (compiler_solution_llpc.cpp). After that, LLPC is called from exactly two places: BuildShaderModule (shader module creation) and BuildGraphicsPipeline/BuildComputePipeline (pipeline creation, on a cache miss). See Topic 3.

3 · Shader compilation

AMDVLK compiles pipelines, not shaders. A shader module is only hashed and preprocessed; when a pipeline is created, LLPC translates each stage's SPIR-V to LLVM IR, links the stages into one module, lowers it with full knowledge of the pipeline state, and has LLVM emit a single ELF that PAL loads.

The pipeline in one picture

  1. XGL: vkCreateShaderModule → PipelineCompiler::BuildShaderModule → LLPC BuildShaderModule, which hashes the SPIR-V and records usage. No ISA is produced yet.
  2. XGL: vkCreateGraphicsPipelines → cache lookups → ConvertGraphicsPipelineInfo builds a Vkgc::GraphicsPipelineBuildInfo from all the Vulkan state.
  3. LLPC front end: per stage, LowerTranslator → SPIRV reader (SPIRVToLLVM) → front-end lowering passes. The stages are then linked into one pipeline module.
  4. LGC middle end: PipelineState::generate → LgcLowering::addPasses: state-dependent lowering, hardware stage mapping, NGG.
  5. LLVM AMDGPU backend: addPassesToEmitFile on target amdgcn--amdpal with CPU gfx10xx/gfx11xx/gfx12xx. It produces ISA plus a PAL metadata note, packaged as an ELF.
  6. PAL: IDevice::CreateGraphicsPipeline reads the ELF with PipelineAbiReader, uploads code with CodeObjectUploader, and turns the metadata into register state.

Step-through: shader module → pipeline → ELF → PAL

SPIR-V → LLVM IR

LowerTranslator is an LLVM module pass that runs the SPIRV reader on one shader stage. Before translating, it optionally runs a SPIR-V optimizer and builds the specialization-constant map from VkSpecializationInfo. llvm::readSpirv parses the binary into a SPIRVModule, and SPIRVToLLVM::translate picks the requested entry point and emits IR. The translator is constructed with an lgc::Builder, so resource and built-in operations become LGC operations that are resolved later, not raw hardware intrinsics.

Front-end lowering (Lowering::addPasses) then cleans up SPIR-V constructs: CFG merges, aggressive inlining, access chains, terminators, globals, memory operations, math precision. Once every stage is lowered, the per-stage modules are linked into one pipeline module.

LGC: pipeline-state-dependent lowering

LGC receives the pipeline state that XGL converted (vertex input formats, color target formats and blend, descriptor layout as user-data nodes, GFX IP, options) through setPipelineState. Its pass list (LgcLowering::addPasses) is where that state is consumed:

PassNeeds which pipeline state
LowerVertexFetchVertex binding/attribute formats and strides, to generate fetch code for VS inputs.
LowerFragmentColorExportColor attachment formats and blend, to pick export formats and conversions.
LowerDescDescriptor layout (resource mapping), to turn descriptor accesses into loads from user data/descriptor tables.
LowerInOutWhich stages exist and how they are merged, to lower inter-stage I/O.
PreparePipelineAbiWhich stages exist, to merge API stages into hardware stages and lay out the PAL ABI.
CheckShaderCacheRuns after CollectResourceUsage, so a stage can be skipped if an identical one was already compiled.

AMDGPU backend → ELF → PAL

LGC creates an LLVM TargetMachine for triple amdgcn--amdpal with a CPU name derived from the GFX IP (getGpuNameString: {11,0,0} → gfx1100) and calls addPassesToEmitFile. Inside LLVM, AMDGPUAsmPrinter::EmitPALMetadata records each hardware stage's entry symbol and register usage into AMDGPUPALMetadata, which is written as a MsgPack note (toBlob). The instruction selection, register allocation and scheduling that produce the ISA are standard LLVM codegen and are not traced on this site.

PAL never interprets the ISA. PipelineAbiReader finds the symbols and metadata; CodeObjectUploader copies the code into GPU memory and applies relocations; the HWL (Gfx9 / Gfx12 GraphicsPipeline::HwlInit) builds the register values it will later write with SET_SH_REG / SET_CONTEXT_REG when the pipeline is bound.

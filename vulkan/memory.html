Memory allocation

vkAllocateMemory runs through every software layer: XGL picks a PAL heap, PAL reserves a GPU virtual address, creates a buffer object in the kernel and maps it at that address, and XGL marks the memory resident for every future submission.

Virtual address vs. physical backing: three separate operations

On amdgpu, a usable allocation is the result of three independent steps, and PAL performs them separately in Amdgpu::GpuMemory::AllocateOrPinMemory:

#WhatPAL calllibdrmKernel
AReserve a GPU VA rangeAssignVirtualAddress amdgpu_va_range_allocnone. The VA allocator lives in user space (dev->va_mgr).
BCreate physical backing (a BO in VRAM or GTT)AllocBuffer amdgpu_bo_allocDRM_AMDGPU_GEM_CREATE → amdgpu_gem_create_ioctl
CMap B at A in the process's GPU page tablesMapVirtualAddress amdgpu_bo_va_op_rawDRM_AMDGPU_GEM_VA → amdgpu_gem_va_ioctl → amdgpu_vm_bo_map

Keeping them separate is what makes virtual (sparse/PRT) allocations cheap. For memory created with flags.virtualAlloc, PAL does step A and then only reserves the range as PRT (Device::ReservePrtVaRange), with no backing. Sparse binding later maps real BOs into pieces of that range. A VkBuffer or VkImage bound to ordinary memory gets no VA of its own. Its address is the memory's VA plus the bind offset (Buffer bind).

Step-through: vkAllocateMemory → kernel

Worked examples: three allocations

1. A 64 MiB upload buffer the CPU writes every frame

VkMemoryAllocateInfo info = {
    .sType = VK_STRUCTURE_TYPE_MEMORY_ALLOCATE_INFO, .allocationSize = 64u << 20,
    .memoryTypeIndex = typeWith(VK_MEMORY_PROPERTY_HOST_VISIBLE_BIT | VK_MEMORY_PROPERTY_HOST_COHERENT_BIT) };
vkAllocateMemory(device, &info, NULL, &mem);
vkMapMemory(device, mem, 0, VK_WHOLE_SIZE, 0, &ptr);

(typeWith stands for the usual "first memory type with these flags" loop.)

  1. Which type? On a discrete GPU without Resizable BAR, XGL's priority order puts the GartUswc type second, after the device-local Invisible type, so the first HOST_VISIBLE | HOST_COHERENT match is GpuHeapGartUswc.
  2. VA: PAL reserves 64 MiB of GPU virtual address space in the default partition (ChooseVaPartition); libdrm hands it out in user space.
  3. Backing: AMDGPU_GEM_CREATE with domain GTT and AMDGPU_GEM_CREATE_CPU_GTT_USWC. For memory private to the process, and when the kernel supports it, PAL adds AMDGPU_GEM_CREATE_VM_ALWAYS_VALID.
  4. Map: AMDGPU_GEM_VA maps the BO at the VA. That is the second and last ioctl for the allocation.
  5. Residency: XGL calls AddMemReference, but because the BO is always-valid, the per-queue reference maps skip it and it never appears in a BO list.
  6. CPU map: vkMapMemory passes PAL's CPU-visible check, then libdrm does one AMDGPU_GEM_MMAP ioctl and an mmap. CPU writes through the pointer are write-combined (fast); reads through it are very slow.

2. A 256 MiB device-local image heap

  1. The first DEVICE_LOCAL type is the Invisible type, so heaps[0] = GpuHeapInvisible.
  2. AMDGPU_GEM_CREATE with domain VRAM and AMDGPU_GEM_CREATE_NO_CPU_ACCESS: the kernel may place it outside the CPU-visible BAR window.
  3. Calling vkMapMemory on it (which the Vulkan spec forbids anyway) reaches PAL's ErrorNotMappable branch and returns VK_ERROR_MEMORY_MAP_FAILED (vk_memory.cpp).

3. The same requests on a Resizable BAR system

  1. PAL reports an Invisible heap of size 0. XGL still exposes the device-local type, but routes it to GpuHeapLocal.
  2. PAL's amdgpu layer gives Invisible the same domain and flags as Local, so all VRAM is CPU-mappable.

How heaps and memory types are derived

PAL describes memory as four heaps. The kernel has two domains. Vulkan exposes memory heaps and memory types. The table connects them, using PAL's default heap flags (Device::InitMemoryHeapProperties), XGL's conversion (PhysicalDevice memory-type setup) and PAL's amdgpu translation (heapToDomain / heapToFlags):

  • Order matters. XGL creates heaps and types in the fixed priority order Invisible, GartUswc, Local, GartCacheable, so memory type indices follow that order on a typical discrete GPU.
  • Heap flags. PalGpuHeapToVkMemoryHeapFlags marks Local and Invisible as VK_MEMORY_HEAP_DEVICE_LOCAL_BIT.
  • Resizable BAR. When PAL reports an Invisible heap of size 0 (all VRAM CPU-visible), XGL routes the Invisible memory type to GpuHeapLocal, and PAL's amdgpu layer treats Invisible like Local.
  • “Local” vs. “Invisible” is only a hint to the kernel. Both are VRAM. The CPU_ACCESS_REQUIRED/NO_CPU_ACCESS flags steer placement inside or outside the CPU-visible BAR window, and the PAL comment notes the kernel may change this at runtime.
  • Device-coherent types for VK_AMD_device_coherent_memory are added as extra types when the GPU supports GL2-uncached access (supportGl2Uncached).

Residency, memory references and the BO list

On amdgpu, a BO that the GPU will touch must either appear in the submission's BO list or be VM-always-valid. The kernel uses the list to validate (and, if needed, move back) every BO before running the job. Vulkan has no residency API, so XGL takes the simplest correct route:

  1. Device::AddMemReference is called for every allocation. It calls IDevice::AddGpuMemoryReferences with pQueue = nullptr, meaning "device-global".
  2. Amdgpu::Device::AddGpuMemoryReferences adds the memory to every queue's m_globalRefMap. Memory created VM_ALWAYS_VALID is skipped, because the kernel keeps it valid in the process VM.
  3. At submit time Queue::UpdateResourceList turns the map into the BO list passed with the CS ioctl (see Topic 5).

PAL requests AMDGPU_GEM_CREATE_VM_ALWAYS_VALID when the kernel supports it and the memory is private to the process (not shareable, not exported, not flippable, not peer-writable). Those BOs share the VM root's reservation object (kernel side), so they never need to appear in the BO list.

Mapping host-visible memory

vkMapMemory → Memory::Map → IGpuMemory::Map. PAL refuses virtual memory and anything not CPU-visible (ErrorNotMappable), which is why Invisible-heap memory types lack HOST_VISIBLE. For a mappable BO, libdrm's amdgpu_bo_cpu_map asks the kernel (DRM_AMDGPU_GEM_MMAP) for the BO's fake mmap offset and then calls mmap on the DRM file descriptor. CPU accesses to VRAM pages go through the PCIe BAR; GTT pages are ordinary system pages, either write-combined (USWC) or cached. How the kernel services the resulting page faults (TTM) is not traced.

Mappings are reference-counted inside libdrm per BO. XGL can keep a mapping alive for the object's lifetime with the skipUnMapMemory setting.

Presentation

Presenting is where the driver hands a finished image to someone else: the X server or a Wayland compositor. This page follows vkAcquireNextImageKHR and vkQueuePresentKHR from XGL into PAL's swap chain, its present scheduler, and the DRI3 and Wayland window systems.

The model

  • Images rotate. The swap chain owns N presentable images. Acquire gives you a free one (the least recently used), present gives it back, and an idle fence says when the compositor is done with it.
  • PAL does the bookkeeping, the window system does the display. The PAL swap chain and present scheduler track which images are free and in which order; a window-system object speaks DRI3/Present (X11) or the Wayland protocol.
  • Synchronization is syncobjs again. With explicit sync, each image has acquire and release timeline syncobjs shared with the compositor, the same DRM objects as Topic 5.

Step-through: acquire → present → X11 / Wayland

Worked example: one frame in FIFO mode

uint32_t index;
vkAcquireNextImageKHR(device, swapchain, UINT64_MAX, imageAvailable, VK_NULL_HANDLE, &index);
/* record and submit rendering that waits on imageAvailable and signals renderDone */
VkPresentInfoKHR present = {
    .sType = VK_STRUCTURE_TYPE_PRESENT_INFO_KHR, .waitSemaphoreCount = 1, .pWaitSemaphores = &renderDone,
    .swapchainCount = 1, .pSwapchains = &swapchain, .pImageIndices = &index };
vkQueuePresentKHR(queue, &present);
  1. Acquire: PAL's generic path waits on m_availableImageSemaphore and returns the least recently used free index. imageAvailable becomes a PAL queue semaphore, which on amdgpu is a DRM syncobj, so your rendering waits for it on the GPU, not on the CPU.
  2. Render: your submission waits on imageAvailable as an AMDGPU_CHUNK_ID_SYNCOBJ_TIMELINE_WAIT chunk and signals renderDone.
  3. Present: Queue::Present turns the wait on renderDone into a queue wait, then calls PresentSwapChain. PAL validates that the image is presentable and passes it to its present scheduler.
  4. To the window system: on Linux the scheduler calls the window system's Present with the image's idle fence. On X11 that is xcb_present_pixmap (or the synced variant with timeline syncobjs); on Wayland it is attach, damage, commit.
  5. FIFO: PAL waits until the request has reached hardware (WaitForLastImagePresented), which is how FIFO throttles the application to the display rate.

Mode differences, from the code

  • Mailbox: acquire searches for unused images (ReclaimUnusedImages) and the present is complete as soon as the image is handed over.
  • Immediate: the only Linux mode that may present inline on the calling thread.
  • FIFO: waits for the last present to reach hardware before completing.
  • When no hardware-accelerated path is available, PAL has a CPU blit fallback (DoCpuPresentBlit).

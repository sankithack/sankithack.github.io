4 · Command buffers & PM4

Recording a Vulkan command buffer means PAL writing PM4 packets into chunks of GPU-visible memory. Nothing reaches the kernel until submission. This page follows vkCmdDraw down to the three DWORDs it produces and takes them apart bit by bit.

Pools, allocators and chunks

Each VkCommandPool owns a PAL ICmdAllocator (vk_cmd_pool.cpp). The allocator manages separate pools for several kinds of data. All are GPU memory carved into uniform chunks:

  • CommandDataAlloc holds the PM4 command streams themselves.
  • EmbeddedDataAlloc / LargeEmbeddedDataAlloc hold "embedded data": tables and constants that PAL writes at record time for commands to reference (the large variant is for allocations over 32 KB).
  • GpuScratchMemAlloc is GPU-only scratch for PAL's internal use.

A CmdStream asks for space with ReserveCommands and gives back what it didn't use with CommitCommands. When a chunk fills, CmdStream::GetNextChunk takes one of the stream's retained chunks or calls CmdAllocator::GetNewChunk. The allocator pops its free list (known idle), then scans its reuse list for chunks whose GPU work has finished (IsIdleOnGpu), and only then creates a new CmdStreamAllocation, split into numChunks chunks. Successive chunks of one stream are chained with chaining packets at each chunk's tail, so at submit time only the stream's first chunk is handed to the kernel as an IB (see Topic 5).

The draw hot path

XGL does little at draw time. CmdBuffer::Draw flushes any changed Vulkan dynamic state into PAL (ValidateGraphicsStates) and calls ICmdBuffer::CmdDraw. That call is an inline jump through m_funcTable.pfnCmdDraw, which the HWL fills with a template instantiation specialized for the GPU and the command buffer's options. The HWL's CmdDraw:

  1. Validates (ValidateDraw): writes dirty state as SET_SH_REG / SET_CONTEXT_REG packets. This covers the bound pipeline's registers, user-data SGPRs (descriptor table addresses, push constants), viewport/scissor, and draw-time values such as NUM_INSTANCES and the vertex offset. The full register sequence is not traced line by line.
  2. Builds the draw packet into reserved space: DRAW_INDEX_AUTO for non-indexed draws, IT_DRAW_INDEX_2 for indexed, IT_DRAW_INDIRECT/IT_DRAW_INDEX_INDIRECT or IT_EXECUTE_INDIRECT__EXECINDIRECT variants for indirect draws.
  3. Commits the space.

Step-through: vkBeginCommandBuffer → vkCmdDraw → PM4

Anatomy of a real packet: DRAW_INDEX_AUTO

This is the packet CmdUtil::BuildDrawIndexAuto writes for vkCmdDraw. The field layouts come from PAL's generated chip headers (PM4_ME_TYPE_3_HEADER, PM4_PFP_DRAW_INDEX_AUTO, VGT_DRAW_INITIATOR). Change the inputs to see the DWORDs change, and click a field to see what it means.

Where the other fields come from: the instance count and first vertex/instance are not in this packet. PAL wrote them during validation as an IT_NUM_INSTANCES packet and as user-data SGPRs that the compiled vertex shader reads. That is why DRAW_INDEX_AUTO needs only a vertex count.

Compute: DISPATCH_DIRECT

vkCmdDispatch follows the same shape: CmdBuffer::Dispatch → ICmdBuffer::CmdDispatch → HWL CmdDispatch → CmdUtil::BuildDispatchDirect. That builds a 5-DWORD packet (header, dim_x, dim_y, dim_z, dispatch_initiator) with shaderType = ShaderCompute. On a compute-only queue the same builder writes into a ComputeCmdBuffer stream that runs on the MEC.

Barriers: ACQUIRE_MEM and RELEASE_MEM

On GFX10+ XGL expresses vkCmdPipelineBarrier in PAL's acquire/release model (useReleaseAcquire). PAL's BarrierMgr turns the source stages into release events (e.g. a bottom-of-pipe RELEASE_MEM event, optionally with cache write-back) and the destination stages into an acquire point (how early in the pipe the CP must wait). Cache invalidations go into an ACQUIRE_MEM. Image layout transitions may add decompression or clear blits through PAL's internal RPM (hw/gfxip/rpm), which is not traced here. One generation difference is visible in the code: on GFX11 the color/depth (RB) caches can no longer be flushed by an ACQUIRE_MEM (assert).
